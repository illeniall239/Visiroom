1. INTRODUCTION
================================================================================

1.1 Purpose
-----------
This document specifies the requirements for "VisualCommerce AI," a system that
enables e-commerce shoppers to visualize products within their own physical
spaces using AI-generated imagery. The system accepts user-uploaded room
photographs, analyzes scene context, and generates photorealistic renderings of
selected products placed within those environments.

1.2 Scope
---------
The system shall provide:
- Web-based interface for image upload and visualization
- Real-time scene analysis (depth estimation, surface detection, lighting)
- AI-powered image generation using Nano Banana/Gemini Flash Image
- Progress tracking and result delivery
- Rate limiting and cost protection mechanisms
- Privacy-preserving data handling

The system shall NOT provide:
- Mobile native applications (web-only MVP)
- Augmented reality real-time overlay
- 3D model manipulation or rotation
- Persistent storage of user room photos without explicit consent

2. OVERALL DESCRIPTION
================================================================================

2.1 Product Perspective
-----------------------
The system operates as a standalone microservice within a larger e-commerce
ecosystem. It integrates with:
- Product Catalog Service (read-only, product metadata)
- User Authentication Service (optional, JWT validation)
- Payment/Credit System (future extension)
- Analytics Platform (generation metrics, conversion tracking)

2.2 Product Functions
---------------------
Major functions categorized by user action:

Image Ingestion:
- FU-1: Accept image uploads (JPEG, PNG, WebP, max 10MB)
- FU-2: Validate image content (must contain room/interior scene)
- FU-3: Generate presigned S3 URLs for direct browser upload

Scene Analysis:
- FU-4: Estimate depth map from 2D image
- FU-5: Segment surfaces (walls, floors, furniture, empty spaces)
- FU-6: Extract lighting parameters (direction, color temperature, intensity)
- FU-7: Detect room type and style characteristics

Generation Pipeline:
- FU-8: Construct contextual prompts from product data + scene analysis
- FU-9: Queue generation jobs with priority routing
- FU-10: Execute Nano Banana API calls with retry logic
- FU-11: Post-process outputs (format conversion, quality optimization)
- FU-12: Deliver results via CDN with time-limited access

User Experience:
- FU-13: Provide real-time progress updates via WebSocket
- FU-14: Support "regenerate with variations" (lighting, placement, style)
- FU-15: Enable user placement adjustment (tap-to-move)
- FU-16: Collect explicit user feedback (thumbs up/down)

2.3 User Classes and Characteristics
------------------------------------

Anonymous Browsers:
- No account required
- Limited to 3 generations per 24-hour period (IP-based tracking)
- No room photo retention
- Primary goal: Reduce purchase hesitation

Registered Shoppers:
- Account-based tracking
- 10 free generations monthly, purchase additional credits
- Option to save room photos for future use (opt-in)
- Access to generation history
- Primary goal: Confident purchase decisions

E-commerce Administrators:
- System monitoring dashboard
- Cost and usage analytics
- Content moderation tools
- Rate limit configuration
- Primary goal: ROI monitoring and abuse prevention

2.4 Operating Environment
-------------------------
Client-Side:
- Modern web browsers (Chrome 90+, Firefox 88+, Safari 14+, Edge 90+)
- Minimum 2Mbps internet connection
- WebSocket support required

Server-Side:
- Cloud infrastructure (AWS/GCP/Azure)
- Container orchestration (Docker, Kubernetes/Railway)
- Python 3.11+ for ML services
- Node.js 18+ for API Gateway and WebSocket handlers
- Redis 7+ for caching and queues
- PostgreSQL 15+ for persistent data

External Services:
- Nano Banana API (via Fal.ai or Google AI Studio)
- S3-compatible object storage
- CDN (CloudFront/Cloudflare)

2.5 Design and Implementation Constraints
-----------------------------------------
- Nano Banana API rate limits: 60 requests/minute (free tier)
- Maximum generation latency: 5 seconds (95th percentile)
- User photo storage: Maximum 24 hours without explicit consent
- Budget constraint: <$0.10 per generation (target: $0.03)
- Browser compatibility: No WebGL requirements (accessibility)

2.6 Assumptions and Dependencies
--------------------------------
- Users possess smartphones with functional cameras
- Nano Banana API maintains <3s generation latency
- Product catalog provides sufficient metadata (dimensions, materials, style)
- Sufficient training data available for room/scene validation classifier
- Users accept 5-second wait time for generation results

-------------------------------------------------------------------------------
3.1.1 IMAGE UPLOAD AND VALIDATION
-------------------------------------------------------------------------------

FR-1.0 Image Upload Interface
    Priority: High
    Description: The system shall provide a drag-and-drop or click-to-upload
    interface supporting JPEG, PNG, and WebP formats.
    
    FR-1.1 Maximum file size shall be 10MB; larger files rejected with
          user-friendly error message.
    
    FR-1.2 System shall generate presigned S3 URLs to enable direct browser
          upload, bypassing application servers for bandwidth efficiency.
    
    FR-1.3 Upload progress shall be visually indicated (0-100%).

FR-2.0 Content Validation
    Priority: High
    Description: The system shall validate that uploaded images contain
    interior/room scenes and reject inappropriate content.
    
    FR-2.1 Images shall be classified using a pre-trained model (e.g., 
          CLIP-based classifier) to detect room vs. non-room content.
    
    FR-2.2 Rejection categories: selfies, outdoor scenes, text documents,
          explicit content, non-photographic images.
    
    FR-2.3 Validation latency shall not exceed 500ms; failures queued for
          async re-validation if model uncertain.

FR-3.0 Placement Interaction
    Priority: Medium
    Description: Users shall specify product placement location.
    
    FR-3.1 Default mode: User taps/click on image to place product anchor.
    
    FR-3.2 Advanced mode (v2): System suggests placement regions based on
          surface detection; user selects from suggestions.
    
    FR-3.3 Placement coordinates (x, y) normalized to 0.0-1.0 range,
          stored with generation request.

-------------------------------------------------------------------------------
3.1.2 SCENE ANALYSIS AND UNDERSTANDING
-------------------------------------------------------------------------------

FR-4.0 Depth Estimation
    Priority: High
    Description: System shall generate depth maps from 2D room photographs.
    
    FR-4.1 Implementation using MiDaS or Depth Anything v2 model.
    
    FR-4.2 Output: 256x256 depth map, normalized 0.0 (far) to 1.0 (near).
    
    FR-4.3 Processing latency: <800ms on GPU-enabled instance.

FR-5.0 Surface Segmentation
    Priority: High
    Description: System shall identify and segment distinct surfaces.
    
    FR-5.1 Using Segment Anything Model (SAM) with custom prompts for
          furniture, walls, floors, ceilings, empty spaces.
    
    FR-5.2 Output: JSON array of segments with class labels, bounding boxes,
          and mask URLs.
    
    FR-5.3 Confidence threshold: 0.75; low-confidence segments flagged for
          manual review or excluded from generation context.

FR-6.0 Lighting Analysis
    Priority: Medium
    Description: System shall estimate environmental lighting parameters.
    
    FR-6.1 Extract dominant light direction (8 cardinal directions + overhead).
    
    FR-6.2 Estimate color temperature (warm 2700K to cool 6500K).
    
    FR-6.3 Detect lighting quality (soft diffused vs. hard direct).
    
    FR-6.4 Output used to guide Nano Banana prompt engineering for
          lighting-consistent generation.

FR-7.0 Room Classification
    Priority: Low
    Description: System shall classify room type and style.
    
    FR-7.1 Room types: living room, bedroom, kitchen, bathroom, office,
          dining room, other.
    
    FR-7.2 Style detection: modern, traditional, minimalist, bohemian,
          industrial, Scandinavian, unknown.
    
    FR-7.3 Classification confidence stored for analytics; low confidence
          defaults to "neutral contemporary" in prompts.

-------------------------------------------------------------------------------
3.1.3 GENERATION PIPELINE
-------------------------------------------------------------------------------

FR-8.0 Prompt Engineering
    Priority: High
    Description: System shall construct optimized prompts for Nano Banana.
    
    FR-8.1 Prompt template structure:
          [Product description] + [Placement context] + [Lighting specification]
          + [Style coherence] + [Quality modifiers]
    
    FR-8.2 Product description derived from catalog: name, materials, colors,
          dimensions translated to natural language.
    
    FR-8.3 Placement context: "placed on [surface type] at [depth] distance"
          using depth map data.
    
    FR-8.4 Lighting specification: "[directional] [temperature] lighting,
          [soft/hard] shadows" from lighting analysis.
    
    FR-8.5 Negative prompts automatically appended: "blurry, low quality,
          distorted, cartoon, illustration, painting."

FR-9.0 Job Queue Management
    Priority: High
    Description: Generation requests shall be managed via priority queue.
    
    FR-9.1 Queue implementation: Redis-backed BullMQ (Node.js) or Celery
          (Python) with visibility timeout.
    
    FR-9.2 Priority levels:
          1. Paid users (highest)
          2. Registered free users
          3. Anonymous users (lowest)
    
    FR-9.3 Job TTL: 30 seconds; exceeded jobs marked failed, user notified.
    
    FR-9.4 Dead letter queue for failed jobs with automatic retry (max 3).

FR-10.0 AI Generation Execution
    Priority: High
    Description: System shall execute Nano Banana API calls.
    
    FR-10.1 API provider abstraction layer supporting Fal.ai, Kie.ai, or
           direct Google AI Studio integration.
    
    FR-10.2 Request payload: constructed prompt, aspect ratio matching
           input image, quality setting (balanced speed/quality).
    
    FR-10.3 Timeout handling: 5-second client timeout with graceful
           degradation to "try again" message.
    
    FR-10.4 Response validation: Check for generation artifacts (blur,
           distortion) using Laplacian variance; flag low-quality for retry.

FR-11.0 Post-Processing
    Priority: Medium
    Description: Generated images shall be optimized for delivery.
    
    FR-11.1 Format conversion: PNG source to WebP for delivery (30% size
           reduction).
    
    FR-11.2 Resolution variants: 1024x1024 (display), 512x512 (thumbnail).
    
    FR-11.3 Optional watermark: "AI Visualization" subtle overlay for
           transparency (configurable per tenant).

FR-12.0 Result Delivery
    Priority: High
    Description: Generated images delivered securely to users.
    
    FR-12.1 CDN upload with 24-hour signed URL expiry.
    
    FR-12.2 Direct URL not exposed; proxied through application for
           access control validation.
    
    FR-12.3 WebSocket notification upon completion with result metadata.

FR-16.0 History and Persistence

    FR-16.3 Export/share functionality: Download PNG, share URL (24hr expiry).

================================================================================
4.1 ARCHITECTURAL PATTERNS APPLIED
================================================================================

-------------------------------------------------------------------------------
Pattern: ASYNCHRONOUS JOB QUEUE (BullMQ/Celery)
-------------------------------------------------------------------------------
Concept: Decouple request acceptance from processing to handle variable
         latency and provide reliability.

Application:
- Generation requests enter Redis-backed queue upon upload completion
- Workers process jobs independently of API request lifecycle
- WebSocket provides async notification upon completion

Benefits Demonstrated:
- Handles Nano Banana API latency (2-3s) without blocking HTTP connections
- Enables retry logic for transient failures
- Supports priority routing (paid > free users)
- Scales worker instances independently of API servers

Interview Talking Point:
"I used a queue to handle the mismatch between user-facing latency requirements
(<5s) and the reality of AI API variance. This also gives us durability—if the
generation service restarts, jobs persist in Redis."

-------------------------------------------------------------------------------
Pattern: CIRCUIT BREAKER
-------------------------------------------------------------------------------
Concept: Prevent cascade failures by failing fast when downstream services
         are unhealthy.

Application:
- Nano Banana API health monitored via periodic health checks
- After 3 consecutive failures, circuit opens (fail-fast mode)
- Queue processing paused, users receive "Service temporarily unavailable"
- Half-open state tests recovery before full traffic restoration

Benefits Demonstrated:
- Protects against runaway retry storms during provider outages
- Preserves queue integrity during partial failures
- Graceful degradation to cached responses or "try again later"

Interview Talking Point:
"The circuit breaker protects our budget too—if Nano Banana is erroring, we
don't want to burn credits on doomed requests."

-------------------------------------------------------------------------------
Pattern: STRANGLER FIG (Incremental Migration)
-------------------------------------------------------------------------------
Concept: Gradually replace legacy functionality by building new services
         alongside old ones, then routing traffic incrementally.

Application:
- Phase 1: New AI generation runs parallel to static product images
- Phase 2: A/B test AI vs. static (50/50 split via feature flag)
- Phase 3: Gradual increase to 100% AI for eligible products
- Legacy system remains as fallback for unsupported categories

Benefits Demonstrated:
- Risk mitigation for new technology adoption
- Data-driven validation of conversion lift before full commitment
- Rollback capability without code deployment

Interview Talking Point:
"We're strangling the old static image system—AI generation runs in parallel
first, then we measure conversion impact before cutting over completely."

-------------------------------------------------------------------------------
Pattern: CQRS (Command Query Responsibility Segregation)
-------------------------------------------------------------------------------
Concept: Separate read and write models to optimize each independently.

Application:
- Writes: Upload metadata, generation requests, user feedback (PostgreSQL)
- Reads: Generation history, analytics dashboards (read replicas + Redis cache)
- Event sourcing: Generation lifecycle events stored for audit/replay

Benefits Demonstrated:
- Analytics queries don't impact transactional performance
- Materialized views for complex aggregations (cost per user tier)
- Event log enables debugging production issues via replay

Interview Talking Point:
"Analytics queries on generation history could slow down the upload pipeline,
so I separated them—writes go to primary PostgreSQL, reads from replicas and
materialized views."

-------------------------------------------------------------------------------
Pattern: BULKHEAD (Resource Isolation)
-------------------------------------------------------------------------------
Concept: Partition resources to prevent failure in one component from
         exhausting shared resources.

Application:
- Separate Redis instances: Job queue (persistence) vs. Rate limiting (fast)
- Separate worker pools: CV analysis vs. Generation vs. Post-processing
- Database connection pools isolated by service tier

Benefits Demonstrated:
- Rate limit check failures don't block generation queue
- CV model memory leaks don't impact API availability
- Resource exhaustion in one pipeline stage contained

Interview Talking Point:
"I isolated the rate limiting Redis from the job queue—if someone hits us
with a DDoS, the rate limiter stays responsive even if the queue is under
heavy load."

4.3 SCALABILITY AND PERFORMANCE STRATEGIES
================================================================================

-------------------------------------------------------------------------------
Technique: HORIZONTAL SCALING WITH STATELESSNESS
-------------------------------------------------------------------------------
Application:
- API servers: Stateless, any request can be handled by any instance
- Session state externalized to Redis
- WebSocket connections: Sticky sessions or shared Redis adapter (Socket.io)

Interview Angle:
"I designed all application layers to be horizontally scalable—no instance
holds critical state, so we can scale from 2 to 20 nodes based on queue depth."

-------------------------------------------------------------------------------
Technique: CACHING STRATEGY (Multi-Layer)
-------------------------------------------------------------------------------
Layers:
1. Browser cache: Product images, static assets (immutable hashes)
2. CDN cache: Generated images (24hr TTL, signed URLs)
3. Application cache: Scene analysis results (1hr TTL for identical uploads)
4. Database cache: Connection pooling, query result caching

Cache Invalidation:
- Product metadata changes: Purge application cache
- New model version: Gradual CDN cache refresh via versioned URLs

-------------------------------------------------------------------------------
Technique: DATABASE OPTIMIZATION
-------------------------------------------------------------------------------
Strategies:
- Write-heavy tables (generations): Partitioned by date (monthly)
- Read-heavy analytics: Materialized views refreshed hourly
- Connection pooling: PgBouncer with transaction-level pooling
- Indexing: Composite indexes on (user_id, created_at) for history queries

-------------------------------------------------------------------------------
Technique: LATENCY OPTIMIZATION
-------------------------------------------------------------------------------
Specific Optimizations:
- Presigned S3 URLs: Bypass application servers for uploads (saves bandwidth)
- WebSocket connection reuse: Avoid HTTP handshake overhead for progress updates
- CV model batching: Process multiple uploads together when queue depth allows
- Image optimization: WebP conversion reduces transfer by 30%

4.4 RELIABILITY AND FAULT TOLERANCE
================================================================================

-------------------------------------------------------------------------------
Concept: IDEMPOTENCY
-------------------------------------------------------------------------------
Implementation:
- Generation requests include client-generated UUID
- Duplicate UUIDs detected and rejected (prevents double-charge on retry)
- Idempotency keys stored in Redis with 24hr TTL

Scenario:
User clicks "Generate" twice due to slow connection—system recognizes duplicate,
returns existing job status instead of creating new chargeable request.

-------------------------------------------------------------------------------
Concept: DEAD LETTER QUEUES
-------------------------------------------------------------------------------
Implementation:
- Jobs failing after 3 retries moved to dead letter queue
- Manual inspection dashboard for failed generations
- Automatic alert to on-call engineer for DLQ depth > 10

Recovery:
- Replay capability: Re-queue with fixed parameters or refund credit

-------------------------------------------------------------------------------
Concept: GRACEFUL DEGRADATION
-------------------------------------------------------------------------------
Fallback Chain:
1. Full experience: CV analysis + Nano Banana generation
2. Degraded: User placement only + generic lighting prompt
3. Critical: Static product image with "visualize coming soon" message
4. Failure: Apology message with email notification when service restored

-------------------------------------------------------------------------------
Concept: HEALTH CHECKS AND OBSERVABILITY
-------------------------------------------------------------------------------
Implementation:
- Liveness probe: HTTP 200 if process running
- Readiness probe: Database and Redis connectivity check
- Deep health: End-to-end generation test with synthetic data
- Distributed tracing: OpenTelemetry spans across upload → analysis → generation

4.5 SECURITY AND PRIVACY DESIGN

-------------------------------------------------------------------------------
Concept: DEFENSE IN DEPTH
-------------------------------------------------------------------------------
Layers:
1. Network: VPC isolation, security groups, WAF for DDoS protection
2. Application: Input validation, rate limiting, authentication

Concept: PRIVACY BY DESIGN (GDPR Compliance)
-------------------------------------------------------------------------------
Implementation:

- Purpose limitation: Separate consent for analytics vs. generation
- Storage limitation: Automatic TTL on user photos (24hr default)
- Data portability: Export user data as JSON via API

Technical Measures:
- EXIF stripping on upload (removes GPS, camera metadata)
- Automated PII detection in logs (credit card patterns, emails)
- Audit logging: Who accessed what user data when

Concept: SECRET MANAGEMENT
-------------------------------------------------------------------------------
Implementation:
- API keys: AWS Secrets Manager or HashiCorp Vault
- Rotation: Automatic monthly rotation for Nano Banana keys
- Injection: Runtime environment variables, never committed to code
